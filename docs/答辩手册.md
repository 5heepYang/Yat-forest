## 一、30 秒电梯陈述（开场用）

> 我们做的是中山大学校园低碳护林小程序。
> 校园里的树有记录但没人管、学生的低碳行为（骑车、光盘、自带杯）做了也没人认，
> 这两件事本来是分开的。我们把它们接成一条闭环：
> **认养一棵真实的树 → 做低碳行为攒碳积分 → 用积分养护这棵树换护林币 → 护林币换校园文创**。
> 技术上有两个特点：树上新点位由 AI 看照片识别树种后直接上架，不需要人工审核；
> 打卡凭证由视觉模型核验，而且核的是"你说是步行去上课，那你是不是真的走了"，
> 不是"你有没有上课"。

## 二、痛点与解法（评委最爱问"解决什么问题"）

| 痛点 | 现状 | 我们的解法 |
|---|---|---|
| 校园树木信息分散、认养没有反馈 | 树木档案在后勤的表里，学生看不到也参与不了 | 地图上每棵树是一个点位，可认养、可浇水施肥、可上报隐患，成长值和等级可见 |
| 低碳行为缺可核验的激励 | 走路上课、光盘、自带杯全靠自觉，没有记录也没有回报 | 日程化打卡 + 视觉模型核验凭证，通过才给积分；积分能换成实物文创 |
| 树木数据靠人工录入 | 采集一个点位要人填名称、树种、坐标，成本高、错误多 | 拍照 → AI 判断是不是树、识别品种 → 直接上架；不是树直接拒绝 |
| 隐患上报容易被薅 | 随手交一张图就能领奖励 | 上报必须带现场照片，视觉模型先判"画面是不是树"，不是树直接拒绝 |

一句话概括：**把"护林"从一次性的活动，变成每天可做、有反馈、有凭证的行为循环。**

## 四、数据存在哪（必答，建议背下来）

**三层：云端数据库（主）+ 云存储（图）+ 本机缓存（加速/离线）**

### 1. 云数据库：6 个集合

| 集合 | 存什么 | 权限 | 谁能读 |
|---|---|---|---|
| `users` | 用户档案：昵称、头像、碳积分、护林币、成长值、护林天数、公开勋章快照 | 所有用户可读，仅创建者可写 | 所有人可读，但只写自己的 |
| `trees` | 树木点位：名称、树种、经纬度、归属人、等级、成长值、状态（正常/隐患） | 所有用户可读，仅创建者可写（实际由云函数写） | 所有人 |
| `tasks` | 日程打卡：标题、时间段、AI 给的低碳方案、是否完成、减碳克数、凭证 | 仅创建者可读写 | 只有本人 |
| `tree_logs` | 成长实拍 + 隐患工单：图片、AI 分析、奖励积分 | 仅创建者可读写 | 只有本人 |
| `goods` | 补给站货架：3 件文创、价格（护林币）、库存 | 所有用户可读 | 所有人 |
| `records` | 兑换小票：「商品名 · 凭证码」，到服务点出示核销 | 仅创建者可读写 | 只有本人 |

> 区别记忆点：**`goods` 是货架，`records` 是小票。**

### 2. 云存储
树木照片、成长实拍、隐患照片都传云存储，数据库里只存 `fileID`（`cloud://` 开头）。
显示时换成临时 https 链接；客户端取不到时由云函数以管理员身份代取。

### 3. 本机 Storage（`ec_state_v1`、`tree_kit_v1`）
缓存全量状态用于秒开（先渲染缓存再拉云端覆盖），以及林地页的本地容器
（每棵树的浇水/施肥/工单/连续天数按树分桶）。**它不是权威数据源，换设备就没了。**

## 五、三个云函数各干什么

| 云函数 | 职责 | 为什么必须放在云端 |
|---|---|---|
| `actions` | **唯一写库入口**：认养、浇水、施肥、兑换、打卡、新增树、隐患上报、实拍、建日程、改资料、清空数据 | 客户端如果直连写库，积分/库存/归属都能被改包伪造；放云端才能做权限和一致性判断 |
| `task-ai` | **AI 网关**：四种能力（识别树种、隐患定级、凭证核验、低碳方案分析），零 npm 依赖（裸 https 调 DashScope） | API Key 绝不能进小程序包；而且统一的 prompt、JSON 解析、失败降级都在这 |
| `notify` | 订阅消息推送（拍照提醒），双通道：云调用失败时用 AppSecret 走 HTTP | 定时触发必须在云端 |

**为什么是三个而不是一个**：`actions` 是业务写库，`task-ai` 是模型调用（耗时长、易超时），
分开后各自的超时/降级互不影响，AI 挂了也不影响认养、兑换这些基本操作。

## 六、数据隔离怎么做（重点题，我们踩过坑，讲出来很加分）

### 机制三层

1. **身份**：用户不需要注册登录。云开发在每次请求里带上 `openid`（同一微信号 + 同一小程序恒定），
   写入时自动在文档上加 `_openid` 字段。**登录是免费的**。
2. **集合权限**：个人集合设为「仅创建者可读写」，云开发会在查询层自动按 `_openid` 过滤，
   即使前端写错查询条件也读不到别人的数据。`trees`/`goods` 是公共数据，设为「所有用户可读」。
3. **写入口收权**：`trees`/`goods` 的写权限在客户端被**主动放弃**——`db.save()` 里直接把
   trees/goods 过滤掉，所有写操作走 `actions` 云函数，云函数用 `getWXContext().OPENID`
   重新判定"你是谁、你能不能改这棵树"。客户端改包也绕不过去。

### 一个真实踩坑（如果评委问"你们遇到过什么技术问题"，讲这个）

上线后发现**每次进小程序都变成新用户、昵称随机**。排查过程：

- 两次进入分别复制身份信息，发现 `openid` **完全一致**
- 云数据库里两条 `users` 文档的 `_openid` 也一致，集合权限也正确
- 但客户端用 `where({_openid: '{openid}'})` 查询**每次都返回空**

结论：官方文档里 `'{openid}'` 这个占位符应由服务端替换成当前用户 openid，
**在我们的环境里没有生效**。于是改成：启动时先调云函数 `whoami`（`getWXContext()` 最可靠）
拿到真实 openid，再用它显式过滤。改完立刻正常，同一个人再次进入能认回自己的档案。

**这条经验的价值**：身份这种东西不能依赖"看起来应该会生效"的语法糖，要有一条能自证的链路。

> 顺带一个隐私边界：**别人的主页看不到积分、护林币、兑换记录、日程**，
> 只能看到昵称、头像、在养的树、以及**已点亮的勋章**（勋章是用户同意公开的成就快照）。

## 七、AI 用在哪（四个场景，讲清楚"为什么这么设计"）

| 场景 | 模型 | 输入 | 输出 | 不通过会怎样 |
|---|---|---|---|---|
| **新增树木识别** | 视觉 | 现场照片 | 是不是树 + 树种 + 置信度 | 不是树 → **直接拒绝、不落库**，提示重拍 |
| **凭证核验** | 视觉/文本 | 打卡凭证图 + 文字 + **这条日程的低碳方案** | 通过/驳回 + 核验到的做法 + 依据 + 减碳量 | 驳回 → 不给积分，提示换一张 |
| **隐患巡检** | 视觉 | 现场照片 | 是否树 + 危险等级 + 处置建议 + 奖励 | 不是树 → 拒绝，不生成工单、不给积分 |
| **低碳方案分析** | 文本 | 日程标题 | 一句低碳做法 + 建议分数 | 失败 → 用默认方案兜底 |

### 三个设计要点（评委容易追问）

1. **核验对象是"做法"，不是"标题"**
   日程写「去教学楼上课」，AI 给的方案是「步行去上课」。要核验的是**有没有步行**，
   不是"有没有上课"。所以核验时把 `title + desc（方案）` 一起给模型，让它先提取做法，
   再判断凭证能否证明这个做法，并检查**距离/时长/速度是否吻合**
   （步行 4~6 km/h、骑行 12~20、跑步 7~12），做法对不上或信息不足一律判否。
   界面上也把这个做法显示出来：「正在核验『步行』」。
2. **失败要能兜底，不能卡死演示**
   - AI 识别失败 → 新增树 fail-open 放行，树种记「未识别」（宁可数据不完美，不能让用户白填）
   - 核验超时 → 明确提示重试，不假装通过
   - 隐患上报 → 失败就拒绝（这条故意不兜底，因为它直接发积分，防薅）
3. **减碳量有上限** `CARBON_CAP = 300g`，防止模型幻觉输出离谱数字。

## 八、项目亮点（挑 6 条讲，多了记不住）

1. **AI 替代人工审核闭环**：用户只填名称 + 拍照，树种由视觉模型识别后直接上架。
   我们把原本的人工审核**整个删掉了**——因为审核依赖管理员身份，普通用户根本触发不到，
   是个"看起来有、实际走不通"的功能。删掉后流程反而通了。
2. **凭证核验针对"做法"**（见上）：这是同类作品里最容易做错的地方——大多数只核"凭证像不像"，
   我们核"你说的做法和凭证数据对不对得上"。
3. **写操作全部收权到云函数**：客户端只做乐观更新，云端是唯一权威。
   积分、库存、树的归属都改不了包。
4. **首屏秒开**：本机缓存先渲染（stale-while-revalidate），云端回来再覆盖；
   地图页并行加载，避免"白屏等数据"。
5. **1.2 MB 的包怎么塞下 9 张插画**：每种树一张扁平插画（8 个树种 + 1 张中性兜底），
   按树种名映射，认不出的按**形态族**（棕榈/针叶/开花/常绿阔叶/落叶阔叶）兜底，
   既不是全员椰子树，也没为冷门树种无限加图。原图裁边、居中、512、减色压缩到 452 KB。
6. **测试是能跑的**：6 套 Node 测试共 212 项断言，用内存假数据库把云函数直接 require 进来跑，
   不联网、不部署。云函数"没部署就测不了"是这类项目的通病，我们用假 SDK 绕过了。

## 九、现场演示脚本（3 分钟主线）

> 演示顺序设计原则：**先给视觉冲击（地图 + 插画），再给 AI 惊喜（识别树种），
> 最后给闭环（攒分 → 认养 → 兑换）**。

| 步骤 | 操作 | 讲解点 |
|---|---|---|
| 1 | 打开小程序，地图页 | 「每棵树是一个真实点位，按树种显示不同插画，金色是我认养的」 |
| 2 | 点「+」→ 拍一棵真树 → 提交 | 「只填名字和照片，树种 AI 识别」→ 等 2 秒出树卡片：「识别为香樟，已上架」 |
| 3 | 反例：拍一本书提交 | 「不是树直接拒绝，不落库」——这条最能说明 AI 是真在判断 |
| 4 | 认养一棵树 | 「扣 300 积分，自动跳林地页，这棵树的插画和成长进度都在」 |
| 5 | 浇水 / 施肥 | 「每天每棵各一次，扣积分涨成长值，同时发护林币」 |
| 6 | 日程 → 加一条「去教学楼上课」 | 「AI 给出低碳方案：步行去上课，减碳约 200g」 |
| 7 | 打卡 → 传一张运动截图 | 「核验对象是『步行』，不是『上课』」→ 通过，积分到账 |
| 8 | 隐患上报 → 拍一张有枯枝的树 | 「AI 定级中危，给处置建议，奖励 100 积分」 |
| 9 | 我的 → 补给站 → 兑换 | 「生成凭证码，到校园服务点出示领取」 |
| 10 | 地图点别人的树 → 看 TA 的主页 | 「只能看到 TA 的树和已点亮勋章，积分和日程是隐私」 |

- [ ] 云函数 `actions` / `task-ai` 都是最新版（改过就一定重传过）
- [ ] `task-ai` 的环境变量 `DASHSCOPE_API_KEY` 有值（没有的话 AI 全部走兜底，效果差很多）
- [ ] 云函数超时设成 20 秒（默认 3 秒，视觉调用会超时）
- [ ] 手机网络正常；准备 3 张演示用图：一张真实树木照、一张 Keep/步数截图、一张"不是树"的照片（书本/黑板）

## 十、Q&A 分级问答

### A 组 · 基础（一定会问）

**Q1：这个项目是做什么的？**
A：见「30 秒电梯陈述」。补一句落地场景：校园绿化服务点核销文创，把线上行为换成线下实物。

**Q2：数据存在哪？**
A：云端数据库 6 个集合（users/trees/tasks/tree_logs/goods/records）+ 云存储放照片 +
本机缓存做秒开。权威数据在云端，本机缓存丢了不影响。

**Q3：云函数是干什么的？为什么不用普通后端？**
A：三个：`actions` 是唯一写库入口（防伪造）、`task-ai` 是 AI 网关（密钥不能进包）、
`notify` 发订阅消息。用云开发是因为**不用买服务器、不用自己写登录**，
openid 就是天然身份，比赛周期内性价比最高。代价是被云开发绑死、没有跨平台能力。

**Q4：用户身份怎么识别？没有注册登录吗？**
A：靠微信 openid（同一微信号 + 同一小程序恒定），云开发写入时自动注入 `_openid`，
查不到档案就静默建档。所以"登录"这一步对用户是无感的。

**Q5：数据隔离怎么做的？**
A：三层：openid 身份 → 集合权限「仅创建者可读写」自动按 `_openid` 过滤 →
写操作全部收权到云函数（客户端不能直写 trees/goods）。
再讲那个 `'{openid}'` 占位符失效的踩坑故事（见第六节）。

**Q6：亮点是什么？**
A：见第八节，挑 2~3 条讲。最推荐讲"删掉人工审核"和"核验做法而不是标题"，
这两个都是**发现问题后主动改设计**，比堆功能有说服力。

### B 组 · 技术细节（老师/技术评委）

**Q7：AI 识别不准怎么办？**
A：三层处理：① prompt 里明确"画面主体是树木/植株即算通过"，避免误杀；
② 品种是泛称（如"乔木"）时降级成"未识别"，不硬编一个错名字；
③ 识别调用失败时 fail-open 放行并标记"未识别"，宁可数据不完美也不让用户白填。
如果真识别错了，用户可以重新上传，或管理员在控制台改 `species` 字段。

**Q8：AI 会不会被一张网图骗过去？**
A：会，这是当前方案的边界，我们没做活体/时间戳校验。我们做的防作弊是：
凭证必须与"低碳做法"匹配（步行要有距离和时长，且速度合理），凭证与做法对不上就判否；
隐患上报必须带照片且先判是不是树。真要更严需要加 GPS 与拍摄时间校验，属于后续工作。

**Q9：为什么减碳量上限是 300 克？**
A：`CARBON_CAP` 防模型幻觉。步行/骑行一次通勤的合理区间在 80~300g，超过基本是模型编的。

**Q10：每天的日程为什么限 10 条？**
A：两条理由：一天排十件事已经够多；更重要的是**每条打卡都要 AI 核验**，
不限量会变成"刷积分"的入口。客户端和云函数两端都校验。

**Q11：并发/性能怎么样？**
A：数据库写入用"确定性 `_id` + 只写变化文档"的增量 upsert，加一条日程只产生 1 次写；
读用本机缓存先渲染。实测模型调用：文本分析约 2.5 秒，视觉核验约 1.4 秒。

**Q12：小程序包体积怎么控制的？**
A：主包 1238 KB / 2048 KB。手段：`packOptions.ignore` 排掉文档和原始素材、
9 张插画压到 452 KB、字体做子集化、图片走云存储不占包。

**Q13：有测试吗？怎么测的？**
A：6 套 Node 测试 212 项断言。云函数用内存假数据库 + 假 `wx-server-sdk` 直接 require 进来跑，
能覆盖认养、每日一次、兑换扣库存、AI 拒绝、上限、清空数据等分支，不需要部署。

### C 组 · 刁钻（大概率会被问，诚实答）

**Q14：这些树的数据是哪来的？真实吗？**
A：种子数据是示例，**真实数据靠现场拍照上传**——这也是我们把"新增树"做成 AI 识别的原因：
采集成本降到一个拍照动作。目前演示库里的树是我们自己采的，规模不大，
但流程是完整的：一个点位 = 一张照片 + 一个坐标。

**Q15：AI 挂了还能用吗？**
A：能。经济类操作（认养/浇水/兑换）不依赖 AI；采集类操作有明确降级：
新增树放行并标"未识别"，核验失败提示重试（不假装通过），隐患上报失败则拒绝（因为它发积分）。

**Q16：跟"蚂蚁森林"有什么区别？**
A：蚂蚁森林的树是线上的虚拟树，我们的树是**校园里真实存在、有经纬度的树**，
你可以在它下面浇水、上报枯枝、看它的成长实拍。线上行为对应线下实体，这是场景差异。

**Q17：为什么没有社交功能（评论、排行榜之外）？**
A：当前范围刻意收窄到"个人行为闭环 + 轻量展示"（排行榜、他人主页）。
加社区要处理内容审核和冷启动，不是本次重点。

**Q18：这个项目最大的技术难点是什么？**
A：身份链路。看起来最简单的一环（`_openid` 查询）反而最容易翻车，
排查花了很久，最后靠"两次进入对比 openid"才定位。这条经验比功能本身更值钱。

**Q19：如果给你更多时间，下一步做什么？**
A：三件：① 凭证加 GPS + 拍摄时间校验，防网图；② 隐患工单接后勤侧处理流程（现在是单向通知）；
③ 树木数据做成可导入的采集工具，让志愿者批量补全校园树种。

**Q20：团队分工？**
A：（按实际填）前端页面 / 云函数与数据层 / AI prompt 与测试 / 视觉素材与文档。
建议每人能讲自己模块的一个坑——评委喜欢听"你踩过什么坑"。

## 十一、万一现场翻车（预案）

| 情况 | 应对 |
|---|---|
| 没网 / 云函数超时 | 走本机缓存，地图和林地页仍可浏览与操作（本地乐观更新），口头说明"云端写操作会失败但界面可用" |

| 评委要看"真实数据规模" | 诚实说规模小、是自采演示数据，重点讲采集与核验流程 |
